# Merge Report: Point-in-Time Master Panel

Explains every decision made while merging `crsp_monthly_stock`,
`crsp_delisting`, `ccm_link_table`, `compustat_fundamentals_annual`, and
`fama_french_5f_momentum_monthly` into one security-month panel at
`data/processed/master_panel.parquet`. Implementation lives in
`src/data_processing/`; full diagnostics (including a firm-coverage-by-year
table and per-column missingness) are regenerated by
`python scripts/run_data_processing.py` into `reports/data_processing/`
(gitignored — see `reports/README.md`). This document is the durable,
git-tracked record of *why* the merge works the way it does; the numbers
quoted below are a snapshot from the most recent run.

**This is data integration, not feature engineering or modeling.** No labels,
targets, or model-ready features are constructed here — see `PLAN.md`.

## Inputs

Reads only from `data/interim/` (the typed, exact-duplicate-free Parquet
files `data_validation` produces from the raw CSVs) — never from
`data/raw/` directly. `crsp_names` is **excluded**: it has no NAMEDT/NAMEENDDT
validity-period columns (see `DATA_DICTIONARY.md`), so it cannot be joined
point-in-time, and using it would risk leaking information about an
identifier that wasn't yet known at a given date.

## Pipeline order and every decision

### 1. Resolve `crsp_monthly_stock`'s conflicting duplicate keys (`dedup.py`)

`data_validation` only removes *exact* full-row duplicates; 3,244 rows (as
profiled then) still share a `PERMNO`+`MthCalDt` key with another row but
differ in other columns. A master panel needs exactly one row per
security-month, so before anything else, each such group is resolved by
**keeping the row with the fewest null values** (ties keep the first row
encountered). On the last full run this resolved **1,638 duplicate-key
groups**, dropping 1,638 rows out of 2,499,809 (0.066%).

*Why this rule:* in every example inspected during data validation, the
"extra" copy in a conflicting pair had null `CUSIP`/`Ticker` where the other
copy had real values — i.e. one copy is a strictly less-informative version
of the other. Keeping the more complete row is a conservative choice that
never discards information the more complete row also has.

*Known limitation:* this rule is generic (fewest nulls across all columns),
not specific to what actually differs between CRSP's two conflicting copies.
If a future data pull has conflicting copies that differ in some other way
(e.g. two different non-null values for the same field), this rule doesn't
try to determine which is "correct" — it only prefers completeness.

### 2. Resolve a point-in-time `gvkey` for every PERMNO-month (`ccm_linking.py`)

For each CRSP security-month, finds the `ccm_link_table` row whose validity
window `[LINKDT, LINKENDDT]` covers that month. `LINKENDDT` being null means
the link is still open (the raw `"E"` sentinel, already parsed to `NaT` by
`data_validation`). Implemented as a backward `merge_asof` on `LINKDT`
(grouped by PERMNO), followed by a filter that drops the match if the
resolved link had already ended by that month — the standard efficient way
to do a point-in-time interval join in pandas.

*Tie-break:* if more than one link is simultaneously valid for the same
PERMNO (not observed in this data — every check during data validation found
zero overlaps, from either the gvkey or the PERMNO side), `LINKPRIM == "P"`
(primary) is preferred, per WRDS's own convention. This is defensive code,
covered by a dedicated unit test with synthetic overlapping data, not
something the real data currently exercises.

*Result on the last full run:* 1,993,028 / 2,498,171 PERMNO-months (79.78%)
matched to a gvkey. The remainder is not a bug — it includes PERMNOs CCM
never links to Compustat at all (non-filing entities, funds, etc.) and
periods before/after a security's link window. See `DATA_DICTIONARY.md` for
the CCM coverage-gap analysis from the validation phase.

### 3. Merge Compustat fundamentals point-in-time (`compustat_merge.py`) — the core look-ahead-bias guard

This is the step that actually prevents using future accounting information.

- **Reporting lag: 6 months after `datadate`.** A fiscal year's fundamentals
  are only attached to CRSP months on or after
  `datadate + 6 months` — never earlier. This follows the standard academic
  convention (Fama and French, 1992/1993) used whenever a confirmed
  filing/announcement date isn't available. This extract has no
  `rdq`-equivalent (earnings announcement date) field, and `apdedate` (26%
  null, meaning unconfirmed per `DATA_DICTIONARY.md`) is **not** used for lag
  purposes — only `datadate` is, uniformly, regardless of a firm's specific
  fiscal year-end month (the lag is fiscal-year-end-relative, not
  calendar-relative, so it's correct for non-December fiscal years too).
- **Shelf life: 12 months after that availability date.** So one fiscal
  year's data is used for the window
  `[datadate + 6mo, datadate + 18mo)` — the classic 6-month-lag,
  12-month-shelf-life annual rebalancing convention. Past that, the data is
  treated as stale and nulled out rather than carried forward indefinitely
  (which would otherwise happen by default with a backward `merge_asof`, if
  a firm's Compustat coverage lapses while its CRSP data continues).
- Both numbers are configurable via `MergeConfig` (`reporting_lag_months`,
  `max_fundamentals_age_months`), not hardcoded inline.
- Implemented as a backward `merge_asof` on `datadate + lag`, grouped by
  `gvkey` — for each PERMNO-month, this picks the most recent fiscal year an
  investor could already have known about, and a newer fiscal year
  automatically supersedes an older one exactly when it becomes available
  (verified by a dedicated test: when two fiscal years become available in
  the same month, the newer one wins).
- Columns dropped: `GVKEY` (redundant with the `gvkey` from CCM linking) and
  `indfmt`/`consol`/`popsrc`/`datafmt`/`curcd` (single-valued in this
  extract — see `DATA_DICTIONARY.md`). Every other Compustat column is kept,
  prefixed `cst_`.
- `cst_available_date` and `cst_age_months` are always populated once a
  match is found (even if later marked expired), so diagnostics can tell
  "never matched anything" apart from "matched, but too stale to use." Only
  `cst_expired` and the nulled-out value columns reflect the expiry itself.

*Result on the last full run:* 1,714,392 / 2,498,171 PERMNO-months (68.63%)
matched to usable (non-expired) fundamentals; 8,471 more (0.34%) matched
something but it had expired. Coverage is much lower in 1999 (579 of 9,363
gvkey-matched PERMNOs) than in later years — see "Known limitations" below;
this is an expected artifact of the panel's start date, not a defect.

### 4. Apply delisting-return adjustments (`delisting.py`)

CRSP's monthly return for a security's *final* month does not include its
delisting return, which is reported separately in `crsp_delisting.DelRet`.
Ignoring it understates the true return investors experienced — a
well-documented source of bias in naive CRSP panels (Shumway, 1997).

- For each PERMNO's single last observed row, if that PERMNO appears in
  `crsp_delisting`, `ret_adj = (1 + MthRet) * (1 + DelRet) - 1`; every other
  row keeps `ret_adj = MthRet`.
- *Why match on "last row" rather than exact calendar date:* checked
  empirically before writing this code — a security's last
  `crsp_monthly_stock` row is in the same calendar month as `DelistingDt`
  for 99.7% of delisting events (15,614 / 15,663), and never more than 31
  days earlier. CRSP's monthly file already extends through the
  delisting month; there's no separate row to append.
- If `MthRet` itself is null in that final row (no trading before
  delisting), it's treated as 0, so `ret_adj` reduces to the delisting
  return alone.
- **Missing `DelRet` (726 / 15,663 rows, 4.6%) is left unadjusted and
  flagged** (`delisting_return_missing = True`), not imputed with a guessed
  proxy value. A common alternative (Shumway's proposal of a -30%/-100%
  proxy depending on delisting reason) was deliberately not implemented here
  because `DelReasonType`'s exact code definitions are unconfirmed (see
  `DATA_DICTIONARY.md`) — applying a reason-dependent proxy would mean
  guessing at semantics this project hasn't verified. This is a decision to
  revisit once those codes are confirmed (see `PLAN.md`'s "Still open" notes
  and "Known limitations" below).
- **Scope limit:** only the delisted security's own final return is
  adjusted. Returns are not chained into a successor security via
  `DelPERMNO` (a separate, more involved "return-splicing" methodology this
  project has not implemented).

*Result on the last full run:* 15,663 PERMNO-months adjusted; 726 of those
left flagged rather than imputed.

### 5. Merge Fama-French factors by month (`fama_french.py`)

No point-in-time logic needed: `fama_french_5f_momentum_monthly` has no
firm-level identifiers, and its `dateff` month-ends match
`crsp_monthly_stock.MthCalDt` exactly (verified 1:1 both ways during data
validation). Plain left join on calendar month; columns prefixed `ff_`.

*Result:* 100% of panel rows matched a factor month on the last full run.

## Survivorship bias

The panel is a **left join from `crsp_monthly_stock` throughout** — every
CRSP security-month is kept whether or not it ever matches CCM or Compustat.
Delisted, unmatched, and never-Compustat-covered securities all remain in
the output; only their `cst_*` columns are null. Nothing is filtered out for
lack of a match at any stage, which is what keeps the panel
survivorship-bias-free.

## Output schema

`data/processed/master_panel.parquet` — one row per (`PERMNO`, `MthCalDt`).
Notable columns beyond the original CRSP fields:

| Column | Meaning |
| --- | --- |
| `gvkey` | Point-in-time-resolved Compustat firm identifier (nullable). |
| `link_matched` | Whether a CCM link was active this month. |
| `cst_*` | Compustat fundamentals (see `DATA_DICTIONARY.md` for field meanings), point-in-time correct. |
| `cst_available_date` | The `datadate + lag` of the fundamentals actually used (or matched-but-expired). |
| `cst_age_months` | Months elapsed since `cst_available_date`. |
| `cst_expired` | Whether the matched fundamentals exceeded the shelf life (values nulled if so). |
| `ret_adj` | Delisting-return-adjusted monthly return. |
| `is_last_obs` / `is_delisted` / `delisting_return_missing` | Delisting bookkeeping flags. |
| `ff_*` | Fama-French factors for that month. |

## Known limitations / not yet handled

- **Coverage ramps up over the panel's first ~2 years.** 1999 shows only
  579 gvkey-matched PERMNOs with usable Compustat data (of 9,363 with a
  gvkey) versus ~5,000-7,800 in most later years — an artifact of the
  6-month lag plus needing a prior fiscal year's data that mostly predates
  this Compustat extract's own 1999-06-30 start, not a bug.
- **No quarterly Compustat data** — only annual fundamentals are merged.
- **`DelReasonType`-dependent delisting-return proxies are not applied** —
  see the delisting section above.
- **No return-chaining through `DelPERMNO`** into successor securities.
- **The residual CCM coverage gaps flagged during data validation** (21
  unexplained PERMNOs, 1,072 unexplained gvkeys — see `DATA_DICTIONARY.md`)
  were not re-investigated here; they remain unmatched in this panel.
- **Universe/sample filters are not applied** — the panel includes every
  security in `crsp_monthly_stock` as provided (no share-code, exchange, or
  other universe restriction). See `PLAN.md`'s open questions.

## Reproducing this

```bash
python scripts/run_data_validation.py   # if data/interim/ doesn't exist yet
python scripts/run_data_processing.py
```

See `src/data_processing/config.py` for every tunable assumption
(`reporting_lag_months`, `max_fundamentals_age_months`, `linkprim_priority`).
