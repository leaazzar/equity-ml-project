# Model Report: Phase 4 First Pass

Explains what was actually built and found running Phase 4 (modeling +
backtesting) for the first time against the real panel, per the design in
`MODEL_DESIGN.md`. Implementation lives in `src/equity_ml/models/` and
`src/equity_ml/backtest/`; full diagnostics are regenerated by
`python scripts/run_modeling.py` then `python scripts/run_backtest.py` into
`reports/modeling/` and `reports/backtest/` (gitignored — see
`reports/README.md`). This document is the durable, git-tracked record of
*why* it works the way it does and what the first real run found; the
numbers quoted below are a snapshot from that run, generated
2026-08-03.

**This is a first pass, not a finished research result.** It exists to
validate that the walk-forward/leakage-safety machinery works end to end
against the real 2.5M-row panel and to get a first read on relative model
performance — not to declare a winning model or a production strategy. See
"Known limitations / not yet handled" below for what a further pass should
address.

## Configuration used

Per `MODEL_DESIGN.md`'s confirmed decisions: 1-month prediction horizon,
monthly rebalance, `is_investable` universe as-is, residual Phase 1-3
data-quality follow-ups explicitly deferred.

- **Target:** forward 1-month `ret_adj`, both raw (`target_raw`) and
  cross-sectionally demeaned within the investable universe
  (`target_demeaned` — the training target, since Section 6's dollar-neutral
  long-short construction doesn't monetize the market-wide return
  component).
- **Universe:** `is_investable == True`, no additional filter — 2,374,996 /
  2,498,171 master-panel rows.
- **Walk-forward:** expanding window, 72-month (6-year) minimum initial
  training window, annual refit, 1-month purge/embargo at every fold
  boundary (`ModelConfig` defaults). **21 folds**, test period spanning
  **2005-02-28 to 2025-12-31**.
- **Features:** `feature_engineering.registry.model_feature_names()` — the
  50-feature recommended list (51 minus `reversal_1m`, collinear with
  `mom_1m`), from `features_model_ready.parquet`.
- **Complete-case training:** no feature is ever imputed (matching the rest
  of this codebase), so a row is used for training/prediction only if all 50
  features and the target are non-missing. This is strict — only 313,490 of
  2,374,996 investable rows (13.2%) qualify, concentrated from 2001 onward
  (essentially zero before that: momentum/volatility features need up to 36
  months of trailing history, and Compustat coverage itself ramps up over
  the panel's first ~2 years — see `MERGE_REPORT.md`).
- **Models run:** three benchmarks (`equal_weight`, `momentum_sort` on
  `mom_12_1`, `fama_macbeth`) and four ML estimators (`ridge`, `lasso`,
  `elastic_net`, `hist_gradient_boosting`), each tuned per fold on a purged/
  embargoed inner train/validation split by validation-fold Information
  Coefficient (MODEL_DESIGN.md Section 5).
- **`random_forest`** (in `estimators.DEFAULT_ESTIMATORS`, fully implemented
  and tested) was **excluded from this run** — see "Compute-scoping
  decisions" below.
- **Portfolio construction:** decile long/short, equal-weighted, dollar-
  neutral, monthly rebalance (`BacktestConfig` defaults).
- **Transaction cost:** 10 bps one-way placeholder (this project has no
  bid-ask-spread/commission data), with a 0/5/10/20/50 bps sensitivity table.

## Compute-scoping decisions (this run only, not a design change)

- **`RandomForestRegressor` excluded.** Benchmarked directly against the
  real complete-case sample before running: a *single* fit at
  `n_estimators=300` (the design's default) took **165.8 seconds** at the
  full ~313K-row sample (18.5s at 50K rows, 65.5s at 150K rows — see the
  timing benchmark in this session's history). A full grid search
  (18 candidates) across 21 folds at that cost would run for hours, not
  minutes. `HistGradientBoostingRegressor` — the same fit taking **0.5
  seconds** at full size — serves as this run's tree-ensemble
  representative. `random_forest` remains in `estimators.DEFAULT_ESTIMATORS`
  and `tests/models/test_tuning_and_estimators.py`'s build/fit/predict smoke
  test; running it for real needs either a much smaller `n_estimators`/grid
  or more compute budget than this pass used.
- **Permutation importance computed for `ridge` and `hist_gradient_boosting`
  only**, across all 21 folds, `n_repeats=3` (~20 seconds for `ridge`, ~5.5
  minutes for `hist_gradient_boosting`) — see "Explainability" below. Not
  run for the other five models in this pass, to keep scope bounded; the
  machinery (`diagnostics.permutation_importance_by_fold`) works identically
  for any `EstimatorSpec`.

## Two real bugs found and fixed running against real data

Both were invisible against the synthetic test fixtures (plain `float64`
throughout) and only surfaced once real WRDS-derived data — some of it in
pandas nullable extension dtypes — flowed through the pipeline:

1. **`information_coefficient` (`tuning.py`) silently propagated NaN.**
   `scipy.stats.spearmanr` returns NaN for an *entire* month if even one
   `(y_true, y_pred)` pair is missing, rather than excluding just that pair.
   This corrupted the `momentum_sort` and `equal_weight` benchmarks' IC
   entirely (`momentum_sort` predicts on every row with a non-missing
   `mom_12_1`, not only complete-case rows across all 50 features the way
   the ML models implicitly do, so a much larger fraction of its scored rows
   had a missing `target_demeaned` near the sample's edges) — every single
   month came back NaN, hiding a real, statistically significant momentum
   signal. **Fixed:** filter to pairs where neither `y_true` nor `y_pred` is
   NaN before calling `spearmanr`, with regression tests
   (`test_information_coefficient_ignores_nan_in_y_true_rather_than_propagating`,
   `..._in_y_pred_too`) asserting a single missing pair no longer zeroes out
   an otherwise valid month.
2. **`fama_macbeth_runner` (`baselines.py`) and `factor_regression`
   (`performance.py`) crashed on real data**, both via the same root cause:
   feature/factor columns read from the real parquet files carry pandas
   nullable dtypes; passing them straight into `np.linalg.lstsq` /
   `statsmodels.OLS` without an explicit `float64` cast produced an
   object-dtype array those libraries can't consume
   (`UFuncInputCastingError` / `TypeError: ufunc 'isfinite' not supported`).
   **Fixed:** explicit `.to_numpy(dtype="float64")` at both call sites.

Neither bug affected the ML estimators' own predictions (scikit-learn's
`check_array` already coerces dtypes internally) or the backtest engine's
return/turnover arithmetic (built from values already cast to plain
`float64` by this codebase's own code, e.g. `targets.py`'s
`pd.Series(np.expm1(...))`) — only the two spots above touched a raw pandas
column with a manual numpy/statsmodels call.

## Results (first pass, 2005-2025 out-of-sample)

### Information Coefficient (signal quality, pooled across all 21 folds)

| Model | IC mean | IC std | IC t-stat | # months |
| --- | --- | --- | --- | --- |
| momentum_sort | 0.0425 | 0.1339 | 4.82 | 230 |
| hist_gradient_boosting | 0.0295 | 0.0808 | 5.53 | 230 |
| elastic_net | 0.0258 | 0.0857 | 4.56 | 230 |
| lasso | 0.0247 | 0.0852 | 4.40 | 230 |
| fama_macbeth | 0.0225 | 0.0760 | 4.50 | 230 |
| ridge | 0.0197 | 0.0754 | 3.97 | 230 |
| equal_weight | NaN | NaN | NaN | 0 |

`equal_weight`'s NaN is expected, not a bug: every prediction is identically
0, so rank correlation is mathematically undefined every month (a
zero-skill baseline, by construction). Every real model has a positive,
statistically significant (t > 3.9) mean IC — `hist_gradient_boosting` has
the *most consistent* signal (highest t-stat, lowest IC std) despite
`momentum_sort` having the highest raw mean IC.

### Backtest performance (net of 10 bps one-way cost, decile long/short)

| Model | Ann. Return | Ann. Vol | Sharpe | Sortino | Max Drawdown | Hit Rate | Avg. Turnover |
| --- | --- | --- | --- | --- | --- | --- | --- |
| fama_macbeth | 15.5% | 15.4% | 1.01 | 1.17 | -46.2% | 65% | 1.15 |
| ridge | 12.5% | 14.0% | 0.89 | 1.39 | -36.8% | 61% | 0.94 |
| hist_gradient_boosting | 15.6% | 22.7% | 0.69 | 0.58 | -71.6% | 63% | 0.91 |
| elastic_net | 10.6% | 16.9% | 0.63 | 0.97 | -53.8% | 57% | 0.84 |
| lasso | 10.1% | 16.9% | 0.60 | 0.87 | -54.1% | 59% | 0.83 |
| momentum_sort | 10.2% | 21.2% | 0.48 | 0.45 | -73.5% | 66% | 0.53 |
| equal_weight | -2.3% | 5.9% | -0.40 | -0.57 | -43.7% | 48% | 0.05 |

The IC ranking and the Sharpe ranking **do not agree** —
`hist_gradient_boosting` has the best signal (highest IC t-stat) but only
the third-best Sharpe, because its long-short portfolio is also
considerably more volatile (22.7% annualized vol vs. 14-17% for the linear
models). `fama_macbeth` and `ridge` — simpler, lower-variance models — turn
a smaller but steadier edge into the best risk-adjusted returns. This is
exactly the kind of finding MODEL_DESIGN.md Section 8 was designed to
surface (signal-quality metrics and portfolio-level metrics answering
different questions), not an inconsistency. `equal_weight`'s slightly
negative net return (rather than exactly zero) is turnover-driven noise from
its own decile split's arbitrary but low-turnover reshuffling, consistent
with its near-zero 5% average turnover and its role as a sanity-check floor.

Sharpe is monotonically decreasing in transaction cost for every model with
nonzero turnover (`reports/backtest/cost_sensitivity.csv`), as expected —
e.g. `fama_macbeth`'s net Sharpe runs 1.10 (0 bps) -> 1.01 (10 bps) -> 0.65
(50 bps); `equal_weight`'s is flat-to-worsening (already near-zero turnover,
so cost has little room to bite, but it only ever subtracts).

### Factor-exposure regression (alpha vs. Fama-French 5 + momentum)

| Model | Alpha (monthly) | Alpha t-stat | R² |
| --- | --- | --- | --- |
| hist_gradient_boosting | 0.0132 | 2.83 | 0.037 |
| fama_macbeth | 0.0119 | 3.76 | 0.079 |
| ridge | 0.0102 | 3.43 | 0.103 |
| elastic_net | 0.0094 | 2.49 | 0.090 |
| lasso | 0.0088 | 2.31 | 0.090 |
| momentum_sort | 0.0077 | 1.55 | 0.047 |
| equal_weight | -0.0021 | -1.81 | 0.032 |

Every ML/Fama-MacBeth model has a statistically significant positive alpha
(t > 2.3) against the known factors — the return isn't just a repackaged
momentum or value tilt. `momentum_sort` itself, unsurprisingly, has the
weakest (and only marginally significant) alpha, since it's a single-factor
sort the regression's own `ff_umd` term partially explains away.

### Explainability: feature/category importance (`ridge` vs. `hist_gradient_boosting`, all 21 folds)

Permutation importance (mean decrease in negative MSE on each fold's inner
validation split, averaged across folds — MODEL_DESIGN.md Section 9),
computed for both a linear model and a tree ensemble specifically so they
can be cross-checked against each other, not just reported in isolation.
Full detail: `reports/modeling/feature_importance_{ridge,hgb}.csv`
(per-feature, per-fold) and `category_importance_{ridge,hgb}.csv` (rolled
up to `feature_engineering.registry`'s nine categories).

| Rank | `hist_gradient_boosting` category | `ridge` category |
| --- | --- | --- |
| 1 (highest) | value | liquidity |
| 2 | momentum | value |
| 3 | volatility | leverage |
| 4 | quality | volatility |
| 5 | growth | quality |
| 6 | liquidity | momentum |
| 7 | leverage | size |
| 8 (lowest) | size | growth |

**The two models do not agree, and that disagreement is itself informative,
not a bug.** `hist_gradient_boosting` ranks `value` and `momentum` highest
— the two most-established characteristics in the published cross-sectional
asset-pricing literature — while `ridge` ranks `liquidity` highest by a wide
margin (`liquidity_dollar_volume` alone accounts for roughly half its total
importance). A plausible read: Ridge's L2-regularized linear fit distributes
credit for anything correlated with the target relatively evenly across
correlated features (its own regularization *shrinks* rather than *selects*,
unlike Lasso/ElasticNet), so a feature like dollar volume — which correlates
with several other things being controlled for (size, general liquidity
effects) — can pick up more of a diffuse linear relationship than a single
narrow signal; `hist_gradient_boosting`'s tree splits, by contrast, can
isolate the specific nonlinear/interaction structure in `value_bm` and
`mom_3m` more directly. Both are legitimate, defensible reads of the same
underlying panel — this is exactly the kind of model-family-specific
attribution MODEL_DESIGN.md Section 9 anticipated needing a cross-check for,
not a case where one model's ranking should simply be trusted over the
other's.

Top individual features: `hist_gradient_boosting` — `value_bm`
(book-to-market) and `mom_3m` by a wide margin, followed by `growth_asset`,
`skew_36m`, `quality_operating_profitability`. `ridge` —
`liquidity_dollar_volume` by a wide margin, followed by `value_cf_yield`,
`liquidity_share_turnover`, `leverage_debt_to_equity`, `vol_12m`. Every
`ridge` importance value is roughly an order of magnitude smaller in
absolute terms than `hist_gradient_boosting`'s (consistent with Ridge's
lower overall IC in the table above — less predictive power to begin with
means less of it to lose when a feature is permuted), so the two models'
*rankings* are comparable, their raw magnitudes are not.

## Known limitations / not yet handled

- **Single horizon only.** `h=1` month was run; `h=3`/`h=12` (mentioned as
  robustness checks in `MODEL_DESIGN.md` Section 1) were not.
- **`random_forest` not run for real** — see "Compute-scoping decisions."
- **Permutation importance computed for two models only** (`ridge`,
  `hist_gradient_boosting`), not the full comparison table.
- **Sector-neutral and score-weighted portfolio variants** (both flagged as
  optional in `MODEL_DESIGN.md` Section 6) were not run — only the default
  equal-weighted, universe-wide decile construction.
- **Hyperparameter grids are intentionally small** (MODEL_DESIGN.md Section
  5's stated tradeoff for nested walk-forward CV's cost) — not an exhaustive
  search.
- **This is one realization of a stochastic pipeline** (`random_state=42`
  throughout, per `configs/config.yaml`'s `project.random_seed`, so it's
  reproducible, but hyperparameter/model-family conclusions from a single
  seed shouldn't be over-read).
- Every Phase 1-3 known limitation still applies unchanged (see
  `MERGE_REPORT.md`, `UNIT_AUDIT_REPORT.md`, `FEATURE_DICTIONARY.md`) — none
  of them were revisited or fixed by this phase, per the project owner's
  2026-08-03 decision to explicitly defer them (`MODEL_DESIGN.md`).

## Reproducing this

```bash
python scripts/run_data_validation.py     # if data/interim/ doesn't exist yet
python scripts/run_data_processing.py     # if data/processed/master_panel.parquet doesn't exist yet
python scripts/run_feature_engineering.py # if features_model_ready.parquet doesn't exist yet
python scripts/run_modeling.py            # writes reports/modeling/ (~6 minutes)
python scripts/run_backtest.py            # writes reports/backtest/ (~15 seconds)
```

`scripts/run_modeling.py` uses every estimator in
`estimators.DEFAULT_ESTIMATORS` by default, **including** `random_forest`
— unlike this report's run, which used a custom, smaller model set for
compute-budget reasons (see above). Expect a `random_forest`-inclusive run
to take on the order of hours, not minutes, at this panel's size unless its
`n_estimators`/grid are reduced first.
